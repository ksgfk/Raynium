# Raynium 文档维护

在 Raynium 仓库工作。先读根 `AGENTS.md` 和 `doc/architecture/overview.md`，
再按任务读取所属文档及代码锚点，不预加载整棵文档树。
调整组织或规范时读取[文档维护](../../../doc/guide/documentation.md)。

## 归属与更新

- 根 AGENTS 保留跨任务约束和按需入口；不借整理改变工程行为或引入无关开发规则。
- `doc/architecture/` 只维护已实现职责、接口、所有权及有依据的理由；overview 是当前实现地图与文档/历史索引。
- `doc/guide/` 维护已有工具支持的操作步骤、验证记录和生效规则。README 只介绍项目现状并提供入口。
- 项目技能放在 `.agents/skills/`，不修改用户全局技能；技能描述维护流程，不复制技术契约。

1. 检查工作树，保留用户改动。对照源码、配置、锁文件和执行证据逐段判断；实现与验证分别核对。
2. 除 `doc/history/` 外只写事实，包括生效约束和可执行步骤。建议、设想、推断、候选方案、未来职责/接口、实施顺序和未实施验收计划均归 history；用户确认的未实现目标也不例外。
3. 不靠删除“建议”等词把设想改成事实。当前页面可说明某能力不存在，但不附未来设计；混合段落保留可证实部分，其余按已有授权归档。
4. 就地更新所属页面，同一事实只保留一份权威说明。合并或删除前搜索引用和独有内容；迁移先保存历史，再清理正文，不丢失方案的职责、数据流、所有权、寿命和取舍。
5. 文档页面采用“适用、权威、锚点”三行头部；锚点使用实际存在的仓库相对路径。AGENTS、README 和 SKILL 不套该格式。
6. 修复索引、入口、技能和源码注释中的引用，包括已移走章节的片段链接。上游来源注明仓库、版本或调查日期和源码路径；RadRay 精确版本以锁文件为准。MC 引用注明版本、类/方法和源码生成入口，不依赖个人目录或忽略缓存的可点击链接。

除非用户明确要求，文档（含 history）不保存 Git hash，包括完整值、缩写和链接 URL 中的值；不因归档、验证或源码引用自动添加。用日期、版本、来源路径和状态说明背景。

设计思考保存到 history，不在当前页面设“提案”“下一步”或“已确认未实现”专区。
不另建词汇表、ADR、研究档案或计划目录；有版本与来源的源码事实留在所属页面，未经授权保存的讨论留在会话。

## 开发历史

只有用户明确要求或同意保存思考、方案、历史、快照、实验或交接，或授权迁移现有非事实文档时，才新增 `doc/history/` 记录；
已有授权直接执行，不重复确认。认为有保留价值时可以简述内容和理由后询问，未回复不阻塞其他工作。
“整理文档”“更新当前设计”和测试通过本身都不构成历史授权。

已有历史记录和附件不修改、不改名、不补注、不删除。新的实现事实更新当前页面，新的思考按授权另存历史。
新增历史采用 `YYYY-MM-DD-主题.扩展名`，注明日期、范围、来源及确认/未实现状态；来源包含未提交工作树时明确写出。区分用户目标、助手建议、源码证据与被替代方案，不把全部推演归为用户决定。归档细节遵从文档维护规范。

## 完成检查

在仓库根运行 `python tools/check_docs.py` 和 `git diff --check`。
核查命令、类型、配置与当前实现；检查脚本不能证明语义或外部网页正确。
搜索当前文档的未来式表述和不存在的接口/模块，逐项核对，不能只做关键词替换；核对迁出内容已保存、已有历史未改动。
检查本次文档改动没有加入用户未明确要求保存的 Git hash，检查范围包含链接 URL。
修改检查器时验证它能拒绝缺失引用。历史内部链接按记录基线理解，不为通过当前检查回写历史。
纯文档整理无需构建游戏；汇报实际改动与检查，不把以前的运行结果写成本次重测。
