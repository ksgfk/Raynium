## 1. 核心架构定稿（两条铁律与五项闭合契约）

### 1.1 坐标、绕序与片元窗口坐标：双后端屏幕坐标恒等，无条件统一 `FrontFace::CW`

- **视口代数与实测事实**：
  - 原版 `VulkanRenderPass` 使用正高度视口 `(0, 0, W, H, 0, 1)`，`NDC (-1, -1)` 落入屏幕 `(0, 0)` 与内存第 0 行，`VulkanRenderPipeline` 固定 `.frontFace(1)` = **`VK_FRONT_FACE_CLOCKWISE`**；
  - D3D12 硬件视口变换本身对 $y_{\text{ndc}}$ 取反 $\frac{1 - y_{\text{ndc}}}{2}H$；当 D3D12 顶点出口再执行一次 `gl_Position.y = -y` 时，两次反射相互抵消：
    $$x_{\text{d3d}} = \frac{x + 1}{2}W = x_{\text{vk}}, \qquad y_{\text{d3d}} = \frac{1 - (-y)}{2}H = \frac{y + 1}{2}H = y_{\text{vk}}$$
  - 两端进入光栅化器的二维屏幕坐标 $(x, y)$、附件内存行号及片元像素中心 `SV_Position.xy` / `gl_FragCoord.xy` **完全恒等**，且两后端光栅化器均以 `+X` 向右、`+Y` 向下定义有向面积，同一三角形在两端具有相同的顺逆时针符号；同时 Vulkan 片元 `gl_FragCoord.w = 1 / clip.w`，D3D12 片元 `SV_Position.w = clip.w`。
- **定稿契约**：
  - **顶点阶段**：Vulkan 保持 `gl_Position` 原样；D3D12 在转换着色器顶点出口统一执行 `gl_Position.y = -gl_Position.y`（常驻地形将投影矩阵第二行取反）；
  - **光栅绕序**：**Vulkan 与 D3D12 所有内部渲染目标 PSO（含常驻地形与即时回放，无论是否开启背面剔除）无条件统一固定 `FrontFace::CW`**，保证背面剔除与 `entity.fsh` 无剔除双面片的 `gl_FrontFacing` / `SV_IsFrontFace` 在双后端完全一致；
  - **片元阶段**：**严禁翻转 `SV_Position.y`**；仅在 D3D12 侧保留 `gl_FragCoord.w = 1.0 / SV_Position.w` 倒数换算；
  - **唯一翻转点**：仅在 `CMD_BLIT_TO_SURFACE` 将源纹理指定 mip 的有效矩形拷贝至 BGRA8 交换链后备缓冲时按像素行翻转（见 §1.4 第 2 条）。

### 1.2 前后端切分铁律：状态走 `FrontendRenderPass`，编译与地形拦截前移至 `RayniumGpuDevice`

- **定稿契约**：
  - `RayniumGpuDevice` **覆写顶层 `GpuDevice.compilePipeline`（绝不实例化 `PipelineBuilder` 与 `SPIRVModule`，全程零 `Spvc` 调用）**；命令录制、参数校验、按名缓存与切管线自动重绑 Uniform、`drawMultipleIndexed` 展开及表面状态机复用公开的 `FrontendCommandEncoder`（通过极薄子类 `RayniumCommandEncoder extends FrontendCommandEncoder` 在 `super.createRenderPass` 置位 `isInRenderPass = true` 之前前置校验 `renderArea` 正宽高与 `long` 无溢出边界）、`FrontendRenderPass`、`FrontendGpuSurface` 与公开 `record` `FrontendRenderPipeline`；
  - 同一 `RayniumGpuDevice` 在设备存续期持有一个 `RayniumCommandEncoder` 及其后端。每次 `createCommandEncoder()` 都返回这一前端实例，所有调用方共享 `isInRenderPass()`、当前 `CommandTape` 和 `BatchSubmission`。`Minecraft` 分别取编码器调用 `blitFromTexture` 与 `submit()`，两次操作属于同一批。成功提交后只轮换内部录制批次，先前创建的 `GpuFence` 继续引用已提交批次。
  - **设备能力前置拦截与常驻地形覆盖就地降级**：在 `RayniumGpuDevice.compilePipeline` 最顶层入口（早于常驻地形降级与 `.rnsp` 查找）对齐 `PipelineBuilder` 先检查设备能力——**当 `pipeline.getPolygonMode() == PolygonMode.WIREFRAME && !deviceInfo.features().wireframeFillMode()` 时记录错误并直接返回 `CompletableFuture.completedFuture(CompiledRenderPipeline.Pending.NULL)`**（使 `WIREFRAME`、`WIREFRAME_TERRAIN`、`WIREFRAME_TERRAIN_MULTIDRAW` 等可选线框管线在不支持线框填充的设备上干净返回空而非延后至创建原生 PSO 报错）；随后识别原版常驻地形管线族（`core/terrain` 及其变体），若检测到资源包覆盖了 `minecraft:shaders/core/terrain.{vsh,fsh}`，就地输出单次明确 `WARN` 日志，**直接跳过着色器编译并在所属线程 `Pending.finishCompile()` 阶段用内置原版地形程序反射与当前 `RenderPipeline` 固定状态注册组装出 `FrontendRenderPipeline`**，确保无外部工具链、空磁盘缓存且挂载自定义地形资源包时 `ShaderManager` 重载 100% 成功，实际地形绘制继续走 `TerrainFeature` 原生 `terrain_*` HLSL。

### 1.3 着色器资产策略（方案 A）：程序级 `.rnsp` 共享、管线级固定状态分离与双阶段跨线程注册

- **构建期预编译包、可选外部同源工具链与 `taskExecutor` / 所属线程严格分工**：
  - 沿用离线同源转换链路（`glslangValidator` → `spirv-cross --hlsl --shader-model 60` → `DXC` 同时编译 DXIL 与按 `group 0` UBO、`group 1` `2*i` Texture + `2*i + 1` Sampler 拆分的 Vulkan SPIR-V，装入 Schema 10 `.rnsp`），移除旧 `rayniumPostTexture` UV 翻转正则与 `SceneBackend` 动态常量块，仅保留 `#ifndef __spirv__` 顶点出口 `-gl_Position.y`、片元 `1.0 / gl_FragCoord.w` 与 `debug_point` 六顶点展开；
  - **严格对齐 `ShaderManager` 双 Executor 线程投递模型与 Native `Owner` 线程守卫**：原版 `ShaderManager` 在所属渲染线程 `reloadExecutor` 上同步调用 `device.compilePipeline(pipeline, shaderSource, taskExecutor)`，由 `compilePipeline` 内部自行将重负载投递至后台 `taskExecutor`，最后再将返回的 `CompiledRenderPipeline.Pending::finishCompile` 接回 `reloadExecutor` 执行（而 Native `bridge.cpp` 强制校验 `environment->IsOwnerThread()`）；因此 `RayniumGpuDevice.compilePipeline` 在入口调用线程上仅执行 $O(1)$ 线框能力快速门禁，随后**立即通过 `CompletableFuture.supplyAsync(..., taskExecutor)` 将全部准备与校验投递至传入的 `taskExecutor` 异步执行（绝不在入口调用线程同步展开源码、哈希或阻塞等待外部编译器）**：后台任务在 `taskExecutor` 上严禁调用 `rn_register_pipeline` 或触碰任何 `rn_renderer` 状态，仅执行纯 Java/CPU 无共享可变状态准备（展开 `#include`、计算规范化 `(VS展开源码SHA-256, FS展开源码SHA-256, 排序宏表)` 查找内置 `.rnsp` 或 `.raynium/shader-cache/`、在显式配置 `-Draynium.shaderToolsDir=...` 时后台调用外部工具链写缓存，以及完成下述全部逐管线反射校验并封装不可变注册描述对象；失败则返回 `CompiledRenderPipeline.Pending.NULL`），**统一延后至渲染器所属线程执行 `Pending.finishCompile()` 时调用 `rn_register_pipeline` 分配 `pipeline_id` 并构造 `FrontendRenderPipeline`**（非所属线程误调 `finishCompile` 直接快速失败抛 `IllegalStateException`）。
- **程序共享产物、跨组平坦前端 Uniform 槽位与逐 `RenderPipeline` 固定/图元拓扑边界（防止同程序异状态串味与跨组碰号）**：
  - 原版存在多组共享完全相同 `(VS, FS, defines)` 但固定状态或顶点步长不同的管线（如 `GUI_TEXTURED` 与 `GUI_TEXTURED_PREMULTIPLIED_ALPHA` 混合因子不同，`OIT_ITEM_GLINT/DEPTH_BOUNDS` 36 B 步长与 `OIT_ITEM_GLINT_SPECIAL/DEPTH_BOUNDS` 44 B 步长不同），同时存在跨绑定组同号资源（如 `CLOUDS` 等 8 条云层管线中 `CloudInfo` 为 `group 0, binding 0` 的 UBO，而 `CloudFaces` 为 `group 1, binding 0` 的 `R8_SINT` `TEXEL_BUFFER`，且 `FrontendRenderPass` 对两者均以单一 `int uniformIndex` + `GpuBufferSlice` 调用后端 `setUniform`）；
  - **从 `.rnsp` 程序条目共享读取的字段仅限**：双后端着色器字节码（或 `shader_program_id`）、着色器活动绑定表 `(name, group, nativeBinding, samplerBindingOrNone, resourceKind, dim)`、最大 Push Constant 字节数以及顶点着色器输入变量的 `(name -> location, expectedBaseType, expectedVectorSize)` 表；
  - **必须取自本次编译请求的 `RenderPipeline` 实例自身的字段（后台校验 + 跨组唯一槽位分配 + 所属线程注册）**：
    1. 后台 `taskExecutor` 阶段对照当前 `pipeline` 执行与 `PipelineBuilder` 等价的逐管线接口校验与平坦槽位分配：校验每个着色器活动资源在 `BindGroupLayout.flattenUniforms(pipeline.getBindGroupLayouts())` 中均存在、资源类别（`UNIFORM_BUFFER` / `COMBINED_IMAGE_SAMPLER` / `TEXEL_BUFFER`）及采样维度匹配（拒绝 1D / 3D 纹理；`TEXEL_BUFFER` 额外校验 `pipelineUniform.gpuFormat() != null` 且在双后端受支持格式内，如 `CloudFaces` 的 `GpuFormat.R8_SINT -> TextureFormat::R8_SINT`），**为每个活动 uniform 分配跨组稠密唯一的 `0 .. U - 1` 前端 `uniformIndex` 写入 `FrontendRenderPipeline.uniformIndices`，同步生成一一对应的后端槽位路由表 `slot -> (group, nativeBinding, samplerBindingOrNone, UniformType, @Nullable GpuFormat texelFormat)`**（彻底消除 `group 0` 与 `group 1` 同 `binding = 0` 的覆盖冲突，回放时对 `TEXEL_BUFFER` 构造带 `texelFormat` 的 `ShaderTexelBufferBinding`）；同时校验各阶段反射 `shaderPushConstantSize <= pipeline.pushConstantSize()`，当前 `pipeline.getVertexFormatBindings()` 各元素按名称配对到 `.rnsp` 反射 `location` 时满足 `expectedBaseType` 一致、**`expectedVectorSize <= format.componentCount()`** 及顶点/颜色附件格式均在受支持集合内（32 位顶点格式支持 1/2/3/4 分量，8/16 位仅支持 2/4 分量；任一校验失败即记录错误并返回 `CompiledRenderPipeline.Pending.NULL`）；
    2. **全量 8 种 `PrimitiveTopology` 精确降级契约**：所属线程 `Pending.finishCompile()` 阶段调用 `rn_register_pipeline` 注册逻辑管线并构造 `FrontendRenderPipeline`（`FrontendRenderPipeline.uniforms()` 传入 `BindGroupLayout.flattenUniforms(pipeline.getBindGroupLayouts())` 以保持 `FrontendRenderPass.validateDraw` 完整校验）：其中 `TRIANGLES`、`QUADS` 与 **`LINES`**（`BufferBuilder` 已将每段宽线复制为 4 顶点，上层使用宽线/四边形索引时自行绑定 `RenderSystem.getSequentialBuffer(LINES / QUADS)` 并调 `drawIndexed`）统一编译为 `gpu::PrimitiveTopology::TriangleList`——**与原版 `VulkanRenderPass` 一致，`drawIndexed` 直接消费前端已绑定的索引缓冲，非索引 `draw(vertexCount, instanceCount, firstVertex, firstInstance)` 则原样直接调用底层 `Draw` 而不二次合成 4 转 6 索引**；`DEBUG_LINES` 编译为 `LineList`；`TRIANGLE_STRIP` 与 `DEBUG_LINE_STRIP` 编译为 `TriangleStrip` / `LineStrip` 且固定 `StripIndexFormat = std::nullopt`（禁用图元重启以同时兼容 `UINT16` 与 `UINT32` 索引缓冲）；仅对 D3D12 原生不支持的 `TRIANGLE_FAN`（编译为 `TriangleList`，将非索引 `draw` 与顺序索引 `drawIndexed` 展开为 `3 * (N - 2)` 扇形索引 `(0, i + 1, i + 2)`）和 `POINTS`（`core/debug_point` 六顶点像素方点，编译为 `TriangleList` + 槽 0 `VertexStepMode::Instance`，将 `draw(N, 1, firstVertex, 0)` 与 `PreparedRenderType` 的 `drawIndexed(N, 1, firstIndex, baseVertex, 0)` 统一转换为从第 `baseVertex + firstIndex` 个点元素起始的 `N` 实例 × `6` 顶点绘制）执行绘制展开。

### 1.4 时序归一铁律：地形锚点、像素级上屏 Blit 与保活时间戳全部进入 `CommandTape`

1. **`CMD_DRAW_RETAINED_TERRAIN`（适配 MC 26.3 两张 OIT 系数纹理、双准备分支汇合 `view_id`、AccessWidener 直读与同一 `RenderPass` 内联连续录制）**：
   - MC 26.3 的 `LevelRenderer.OIT_COEFFICIENT_COUNT = 8`，每张 RGBA16F 附件承载 4 个小波系数，实际 **`OIT_TRANSMITTANCE_TARGET_COUNT = 2`（仅 `Coeff0`、`Coeff1` 两张纹理，索引 `0..1`）**；
   - `LevelRenderer` 根据 `usingMultiDrawIndirectForTerrain` 分别调用 `prepareChunkRendersIndirect` 或 `prepareChunkRenders` 构造 `ChunkSectionsToRender`：统一在两条准备路径返回 `ChunkSectionsToRender` 的汇合处采集世界视图快照追加至本批 `views[]`（支持 Headless `0` 份、常规帧 `1` 份、`grabPanoramixScreenshot` 单批 `6` 份），并将分配到的 `view_id` 直接挂载到该 `ChunkSectionsToRender` 实例上，杜绝间接绘制分支漏挂或串用上一视图编号；
   - 在已接入 Loom 构建与运行期的 `src/client/resources/raynium.accesswidener` 中开放 `OitRenderPassProvider$Parameters` 的 `depthBoundsTargetView` 与长度为 `2` 的 `transmittanceTargetViews` 字段访问（编译期与标准 Gradle `test`/`nativeTest` JUnit 均直接生效，无需运行期 Mixin `@Accessor` 强转）；在 `ChunkSectionsToRender.renderGroup` 与 `renderOit` 已解析完 `lightmap` 并打开目标 `RenderPass`（即将调用 `renderLayers`）的位置拦截并委托公开辅助入口：
     - 从当前 `ChunkSectionsToRender` 实例自身读取关联的 `view_id`，连同层组 / `OitStage`、线框标志、`atlas`、`lightmap`、`sampler` 一并写入**当前正处于打开状态的 `RenderPass` 指令流**（同时将对应地形层的原版 `RenderPipeline` 通知 `VisualValidation.pipeline(...)`，保持绕过 `renderLayers` 后的视觉验证管线覆盖统计完整）；
     - 按 `OitStage` 精确编码采样输入：`DEPTH_BOUNDS`（及非 OIT 层组）不附带 OIT 采样视图；`TRANSMITTANCE` 附带 `depthBoundsTargetView`；`ACCUMULATE` 附带 `depthBoundsTargetView` 与 `transmittanceTargetViews[0..1]` 共两张系数视图；
     - **保持同一 `RenderPass` 前后穿插即时绘制的附件与全量图形绑定状态连续性**：原版 `LevelRenderer.executeSolid` 在同一打开的 `RenderPass` 内先调用 `chunkSectionsToRender.renderGroup(OPAQUE)` 再紧接调用 `featureFrame.executeSolid(renderPass)` 绘制实体与方块实体而不关闭 Pass，且合法调用序列（如 `setPipeline(P) + setUniform + pushConstants → Draw A → 地形 → Draw B`）在地形之后无需再次调用 `setPipeline` 或 `pushConstants`；Native 侧**严禁将 `CMD_DRAW_RETAINED_TERRAIN` 拆为重新执行附件清屏/加载的独立光栅节点**，而是向当前正在构建/录制的同一个 `RDGRasterPassBuilder` 声明地形缓冲与纹理读依赖、在同一个 `GraphicsCommandEncoder` 内直接内联录制地形绘制，结束后不仅立即恢复该 Pass 当前的 `Viewport` 与有效 `Scissor`，还将回放器跟踪的当前 Pass 硬件已应用状态（**当前 `PSO`、按 `P` 布局组装的各组 `ShaderParameterSet` 及动态偏移、`PushConstants` 字节块、各槽 `VB`、`IB` 与模板参考值**）全部标脏，确保紧随其后的 `Draw B` 即便无前置设置指令也会在绘制前完整重绑 `P` 的管线、参数集与常量。
2. **`CMD_BLIT_TO_SURFACE`（区分缺失采样用途回退与格式可采样性，支持不等尺寸像素级翻转）**：
   - `FrontendGpuSurface.blitFromTexture` 对源颜色纹理仅要求 `USAGE_COPY_SRC`（不强制声明 `USAGE_TEXTURE_BINDING`），且原版 `VulkanGpuSurface` 取 `copyW = min(swapchainW, view.getWidth(0))`、`copyH = min(swapchainH, view.getHeight(0))` 从 `view.baseMipLevel()` 执行 1:1 像素翻转拷贝而不做全屏归一化拉伸：
     - **区分“源纹理未建采样用途”与“格式本身不支持浮点采样”**：
       1. 对支持浮点 `output` 着色器采样的 1/2/4 通道及紧缩颜色纹理格式（`UNORM` / `SNORM` / `FLOAT` / `RGB10A2_UNORM` / `RG11B10_FLOAT`；三通道 `RGB8`/`RGB16`/`RGB32` 纹理格式在创建入口显式禁止，见 §1.5 第 2 条），`rn_create_texture` 在单采样 2D 颜色纹理声明 `USAGE_COPY_SRC` 时默认附加 `TextureUse::Resource`，回放时直接采样源纹理的 `baseMip`；若源纹理属于上述可采样格式但未附带 `TextureUse::Resource`，回放时先经 RDG 同格式 `CopyTextureToTexture` 将源 `baseMip` 的 `(0, 0, copyW, copyH)` 拷入尺寸为 `(copyW, copyH)`、仅含单级 mip 的瞬态可采样纹理，**此时 `output` 着色器固定读取该瞬态纹理的 `mip 0`**（而非原 `baseMip`）；
       2. 对不支持浮点采样的纯整数颜色格式（`UINT` / `SINT` / `RGB10A2_UINT`，同格式拷贝后仍无法绑定至浮点 `output` 采样器），直接在 `RayniumGpuSurfaceBackend.blitFromTexture` 录制入口（早于 `FrontendGpuSurface` 置 `hasBlittedTexture = true` 及写入 `CommandTape`）当场抛出 `IllegalArgumentException`（Native `rn_submit_frame` 仅保留防损坏字节流兜底拒绝）；
     - `CMD_BLIT_TO_SURFACE` 显式编码 `(textureId, baseMip)`；鉴于 `RadRay` 默认 `ResolveView(source, Resource)` 仅绑定 `BaseMipLevel = 0, MipLevelCount = 1`，`ImmediateReplayFeature` 在 `output` Pass 的 `Prepare` 回调中**显式按 `{.Range = {0, 1, targetMip, 1}, .Usage = TextureViewUsage::Resource}` 解析单级采样视图**（直接采样源纹理时 `targetMip = baseMip`，走单级瞬态中转纹理时 `targetMip = 0`），计算 `copyW = min(swapchainW, srcMipW)`、`copyH = min(swapchainH, srcMipH)`，设置 `Viewport(0, 0, copyW, copyH)` 与同尺寸 `Scissor`（交换链尺寸大于源纹理时按需清黑底或保留外围确定性初态），并在 `output` 片元着色器中统一以相对于该单级视图的 **`lod = 0`** 执行整数坐标 `texelFetch(src, ivec2(svPos.x, copyH - 1 - int(svPos.y)), 0)`，将 `SwapChain::Present` 留在 `rn_submit_frame` 末尾。
3. **`CMD_WRITE_TIMESTAMP`（打点 Pass 顺序屏障、前置越界拦截、物理查询池与读回缓冲同按 `FrameSlot` 隔离及 CPU 逻辑槽缓存发布）**：
   - **保活与顺序屏障合一规则**：顶层 `CommandEncoder.writeTimestamp` 创建的节点以及**所有包含 Pass 内 `RenderPass.writeTimestamp` 的光栅 Pass**，在声明构图时**一律同时标记 `.NeverCull()` 并调用上游 `RDGBuilder::AddOrderBarrier`**——不仅防止后继整幅清屏裁掉被解析的查询槽，更防止后继无资源依赖的独立 `Copy`/`Upload` 节点被调度器提至该打点光栅 Pass 之前重排；
   - **前置严格下标校验与关联 `BatchSubmission` 的免回滚槽位状态机**：鉴于原版 `FrontendCommandEncoder` 与 `FrontendRenderPass` 均误将 `index == pool.size()` 放行（条件写成了 `index <= pool.size()`），`RayniumCommandEncoderBackend` 与 `RayniumRenderPassBackend` 在修改任何 Java 槽位状态或写入 `CommandTape` 之前，**先严格校验 `0 <= index && index < pool.size()`（违约立即抛 `IllegalStateException` 且保持池内原槽位状态丝毫不变）**。校验通过后，`RayniumQueryPool` 将该逻辑槽直接关联到当前录制批次对象 `BatchSubmission`（初始为 `RECORDING`），使上一轮已完成旧值即刻失效；若批次成功提交（含 L0 表面异常下的离屏 `RunFrame()`），`BatchSubmission` 转为 `SUBMITTED(seq)`，直至该批次完成并将结果发布至 CPU 侧逻辑槽缓存后才可读出本轮新值；若批次因 L1 终态故障置为 `FAILED`，查询池读取时见所属 `BatchSubmission` 处于 `RECORDING` 或 `FAILED` 态直接返回 `OptionalLong.empty()`，实现 $O(1)$ 零逐槽回滚；
   - **物理 `QueryPool` 与 GPU `Readback` 缓冲成对按 `FrameSlot` 隔离（根除同批重复写与跨帧 `nonCoherentAtomSize` 缓存行竞争）**：与 `RenderGraphFramePipeline` 内部剖析池设计一致，Native 将按需扩容的物理时间戳 `gpu::QueryPool` **及其配套持久映射 `Readback` `gpu::Buffer` 成对归属到各个 `FrameSlot`**（用户侧逻辑查询池仅维护纯 CPU 侧逻辑槽数组，不跨帧共享 GPU 读回缓冲）：
     1. 回放时统计当批 `CMD_WRITE_TIMESTAMP(poolId, logicalSlot)` 总次数 `N`：**当 `N == 0` 时，直接跳过本批查询池扩容及首尾查询 `CopyPass` 挂载**（绝不录制 `ResetQueryPool(0, 0)` 或 `ResolveQueryData(0, 0)` 触发 RHI 空范围校验失败，仅在复用该 `FrameSlot` 前正常收割上一轮已完成查询结果并清零该槽在途计数）；当 `N > 0` 时，为每一次打点分配当前 `FrameSlot` 内单调递增的独立物理槽 `physIdx`（`0 .. N - 1`），并记录本批每个 `(poolId, logicalSlot)` 最后一次写入对应的 `lastPhysIdx`；
     2. 仅当 `N > 0` 时，由构图最前端 `.NeverCull() + AddOrderBarrier` 的前导 `CopyPass` 执行 `ResetQueryPool(slotQueryPool, 0, N)`，并由构图最末端 `.NeverCull() + AddOrderBarrier` 的收尾 `CopyPass` 对该 `FrameSlot` 专属读回缓冲依次执行 `ReadbackState -> CopyDestination` 屏障、单次连续 `ResolveQueryData(slotQueryPool, 0, N, slotReadbackBuffer, 0)` 以及 `CopyDestination -> HostRead` 屏障；
     3. 当含 `N > 0` 打点的 `FrameSlot` 所属提交序号 `seq` 在 Fence 上完成后（轮询同步或下轮复用该槽开始前），Native 对已完全脱离 GPU 在途访问的 `slotReadbackBuffer` 执行 `InvalidateMappedRange(0, N * 8)`（绝不会因 Vulkan `nonCoherentAtomSize` 扩张误触另一 `FrameSlot` 正在 GPU 上写入相邻逻辑槽的缓冲），随后仅当目标逻辑槽当前记录的最新提交序号仍等于 `seq` 时，将 `slotReadbackBuffer[lastPhysIdx]` 拷贝发布到 CPU 侧逻辑槽缓存。

### 1.5 持久映射缓冲同步、双后端对齐判别打包与无 30s 误杀 `GpuFence`

1. **缓冲三级分配、`MAP_READ` 正交约束与局部暂存回写（含未关闭长驻可写映射提交期自动刷新）**：
   - **`USAGE_MAP_READ` 正交性前置约束**：对齐 WebGPU 与 `RadRay` D3D12 `ReadBack` 堆约束（且与 MC 26.3 全量 `createBuffer` 100% 仅以 `USAGE_MAP_READ | USAGE_COPY_DST` 使用一致），`RayniumGpuDevice.createBuffer`（及 `rn_create_buffer` 预检）要求凡含 `USAGE_MAP_READ` 的缓冲除忽略 `USAGE_HINT_CLIENT_STORAGE` 外仅可组合 `USAGE_COPY_DST`；若同时携带 `USAGE_MAP_WRITE` 或顶点/索引/Uniform/`COPY_SRC` 等 GPU 消费用途，创建期立即抛出 `UnsupportedOperationException`，杜绝为不存在的同步读写混合映射在 `mapBuffer()` 内引入阻塞式 GPU 读回停顿；
   - 所有 `GpuBufferSlice.MappedView.data()` 都向调用方提供原生字节序的 `ByteBuffer`。在 `MemorySegment.asByteBuffer()` 及任何 `slice()`、`duplicate()` 或只读视图转换之后，对最终返回的视图执行 `.order(ByteOrder.nativeOrder())`。这同时适用于持久上传映射、`MAP_READ` 主机内存与设备缓冲的可写暂存切片。`Lightmap` 的 `Std140Builder.putFloat` 和 `Screenshot` 的 `getInt` 都直接使用该视图的字节序。
   - **纯 `MAP_WRITE`（不含 `COPY_DST`）**：创建 `MemoryType::Upload` + `ResourceHint::PersistentMap`；除在 `MappedView.close()` 及瞬态块封口时登记脏区间 `(bufferId, offset, length)` 外，鉴于原版 `StagingBuffer.PersistentlyMapped` 在构造时打开可写映射后跨多帧保持打开、在调用 `MappedView.close()` 之前即录制 `copyToBuffer` 并执行 `submit()`，`RayniumGpuDevice` 同时维护**当前仍处于打开状态的可写持久映射视图集合**——每次 `rn_submit_frame` 时将已关闭脏区间与当前所有仍打开的可写映射区间一并填入 `dirty_mapped_ranges[]`（已关闭脏区间提交后清空，仍打开视图继续保留至其 `close()`），在 `RunFrame` 前统一调用 `Buffer::FlushMappedRange`（D3D12 与 host-coherent Vulkan 下为空操作，非 coherent Vulkan 分配下确保主机写入对本次提交可见）；
   - **纯 `MAP_READ`（`USAGE_MAP_READ | USAGE_COPY_DST`，仅允许 `map(offset, length, true, false)` 只读映射，主机内存承载 + 按 `FrameSlot` 隔离 `ReadBack` 暂存 + 按 `CommandTape` 顺序主机发布，根除跨批 `nonCoherentAtomSize` 竞争）**：`rn_create_buffer` 为纯 `MAP_READ` 缓冲分配零初始化的持久堆外主机内存作为 `mapped_ptr`（GPU 绝不跨批次共享直写同一 `VkBuffer` 缓存行），同时像 §1.4 第 3 条的时间戳池一样在每个 `FrameSlot` 维护专属独立的 `MemoryType::ReadBack | PersistentMap` GPU 读回暂存缓冲 `slotReadbackStaging`（VMA 保证不同 `VmaAllocation` 按 `nonCoherentAtomSize` 对齐隔离）：
     - 同一批次 `k` 内写入 `MAP_READ` 目标缓冲的三类命令统一按 `CommandTape` 顺序登记发布项 `(bufferId, dstOffset, tightRowBytes, rows, srcRowPitch, source)`：**鉴于 FFM 输入数组指针仅借用至同步 `rn_submit_frame` 返回为止（返回后 Java 立即复位复用或扩容释放录制缓冲），`writeToBuffer` 的源字节必须在 `rn_submit_frame` 返回前同步拷入 `FrameSlot[k]` 自有的 CPU 字节存储 `slot.inlineReadbackBytes`（若当批未成功上队则由 `ScopeGuard` 一并清空）**；`copyToBuffer` 在 RDG `CopyPass` 中将源 GPU 缓冲拷入 `slotReadbackStaging`；`copyTextureToBuffer`（颜色及单平面整幅深度）直接按设备有效偏移对齐与 `alignedRowPitch` 单次拷入 `slotReadbackStaging`（无需额外瞬态非对齐逐行 GPU 拷贝，构图末尾将该槽 `slotReadbackStaging` 转换至 `BufferState::HostRead`）；
     - 每当已完成序号推进越过 `seq_k`（含常规轮询及 `GpuFence.awaitCompletion` 返回 `true` 前），Native **仅对已完成且 100% 脱离 GPU 在途写入的 `FrameSlot[k].slotReadbackStaging` 执行一次 `InvalidateMappedRange`**（即使下一批次 `B` 正在 GPU 上写同一逻辑 `MAP_READ` 缓冲的相邻 4 字节，也因落在另一 `FrameSlot` 的独立 `VmaAllocation` 上而零 `nonCoherentAtomSize` 缓存行竞争），随后按 `(seq_k, tape_order)` 严格顺序将本批各发布项的精确字节/紧凑行拷贝写入未关闭目标 `MAP_READ` 缓冲的主机内存，最后由 Java 按录制顺序依次调用 `callback.run()`，只读 `MappedView.close()` 仅解除映射引用而绝不回写；
   - **可写设备缓冲（`USAGE_MAP_WRITE | USAGE_COPY_DST` 等不含 `MAP_READ` 的混合用途，仅允许 `map(offset, length, false, true)` 只写映射，由 `MappedView` 自持切片跨批次保活）**：创建 `MemoryType::Device` 缓冲，**不维护整块常驻 CPU 影子内存，也不从打开时所在批次的可轮转 `TransientBlockAllocator` 借用切片**（防止 `map` 与 `close` 跨越多次 `submit` 与瞬态块轮转复用时悬空覆盖），而是由打开的 `MappedView` 自身独立持有精确 `length` 字节的堆外暂存切片，直至调用 `MappedView.close()` 时才将该切片字节拷入**关闭当下活跃批次**的 `CommandTape` 瞬态上传流并追加目标区间 `[offset, offset + length)` 的 `CopyBufferToBuffer`（随该关闭批次的 Fence 完成后自然释放），既避免跨帧锁死瞬态池，又保证局部写入绝不覆盖区间外已由 GPU 写入的数据。
2. **显式禁止三通道 `RGB*` 纹理格式、单平面深度整子资源拷贝/读回边界、同资源非重叠拷贝拆分与双向纹理↔缓冲设备对齐中转**：
   - **纹理入口快速拒绝三通道 `RGB*` 格式（保留 32 位三通道顶点属性原生支持）**：MC 26.3 全客户端纹理零次使用 `RGB8_*` / `RGB16_*` / `RGB32_*`（`DefaultVertexFormat` 仅使用 32 位三通道顶点属性 `RGB32_FLOAT` 与 `RGB32_SINT`，对应 `RadRay::gpu::VertexFormat` 原生提供的 `FLOAT32X3` / `SINT32X3` / `UINT32X3`；8/16 位枚举仅含 `X2`/`X4`），且桌面硬件与 D3D12 无三通道 2D 最优平铺纹理支持。因此不做 `RGBA*` 伪装承载与逐像素扩缩通道转换，直接在 `RayniumGpuDevice.createTexture`（以及 `compilePipeline` 的 `ColorTargetState` 附件格式校验与 Native `rn_create_texture` 预检）对 `format.componentCount() == 3` 的三通道纹理请求快速失败抛出 `UnsupportedOperationException`，彻底消除无调用死代码与伪造 Alpha 通道的混合语义隐患。
   - **深度纹理间拷贝与深度读回显式契约（覆盖 `RenderTarget.copyDepthFrom` 与 Vulkan 深度 4 字节对齐下限）**：
     - **`copyTextureToTexture`**：颜色格式支持整幅与子矩形同格式拷贝；单平面无模板深度格式（`D16_UNORM`、`D32_FLOAT`）消费上游放开的**整子资源** `CommandBuffer::CopyTextureToTexture`（要求 `destX == 0 && destY == 0 && sourceX == 0 && sourceY == 0` 且宽高等于源与目标该 mip 完整尺寸，覆盖 `RenderTarget.copyDepthFrom`）；局部子矩形深度拷贝或含模板格式（`D24_UNORM_S8_UINT`、`D32_FLOAT_S8_UINT`、`S8_UINT`）纹理间拷贝在 `RayniumCommandEncoderBackend` 录制入口当场抛出 `UnsupportedOperationException`；
     - **`copyTextureToBuffer`（深度与模板边界及实际对齐行距）**：单平面深度格式（`D16_UNORM`、`D32_FLOAT`）仅支持**整子资源**读回（`x == 0 && y == 0` 且宽高等于该 mip 完整尺寸），走既有带 `TextureAspect::Depth` 的整子资源 `CommandBuffer::CopyTextureToBuffer`；**计算有效偏移对齐与行距时严格匹配 RHI 整幅深度规则（D3D12 按 `512 B` / `256 B`，Vulkan 强制抬升下限至 `max(4, TextureDataPlacementAlignment)` 与 `max(4, TextureDataPitchAlignment)`——例如 `3 × 2` 的 `D16_UNORM` 紧凑行宽为 `6 B`、总计 `12 B`，在 `pitchAlignment = 1` 的 Vulkan 设备上仍按 `alignedRowPitch = 8 B`、总计 `16 B` 访问）**：目标为 `MAP_READ` 时按 `effectivePlacement` 与 `alignedRowPitch * height` 直接拷入当批 `FrameSlot` 的 `slotReadbackStaging`，在批次完成后逐行紧凑发布至目标主机内存；目标为 `Device` 缓冲时在当前 RDG GPU 时间线上判断——同时满足 `offset % effectivePlacement == 0`、`tightRowBytes == alignedRowPitch` 且容量充足时直接录制 `CopyTextureToBuffer` 写入目标缓冲，否则先拷入容量为 `alignedRowPitch * height` 的瞬态对齐 `Device` 缓冲再按行录制 `height` 次 `tightRowBytes` 字节的 `CopyBufferToBuffer` 紧凑写入目标缓冲（双后端 `BufferCopyOffsetAlignment` 均为 `1`）；局部子矩形深度读回或含模板格式读回在录制入口当场抛出 `UnsupportedOperationException`。
   - **同资源不重叠区间拷贝的瞬态两阶段拆分（规避 RDG 整资源状态冲突）**：`RDGBuilder` 按整资源粒度追踪屏障，同一 `CopyPass` 对同一句柄同时声明 `CopySource` 与 `CopyDestination` 会因状态冲突构图失败；因此对 `copyToBuffer`（Java 录制入口先拦截并抛 `IllegalArgumentException` 拒绝同缓冲重叠区间，放行合法同缓冲不重叠区间）与 `copyTextureToTexture`（Java 录制入口拦截同纹理同子资源重叠拷贝，放行异 mip/层拷贝），当 `ImmediateReplayFeature` 检出源与目标为同一资源句柄时，自动经等尺寸瞬态 RDG 缓冲/纹理拆分为两个有依赖的 `CopyPass`（`源 -> 瞬态`、`瞬态 -> 目标`）。
   - **双向颜色纹理↔缓冲设备对齐判别与回退**：`RadRay` 在双后端均校验 `TextureDataPlacementAlignment` 与 `TextureDataPitchAlignment`，而前端允许任意字节偏移与紧凑行宽（如 `BitmapProvider` 在纯映射缓冲上以偏移 `4 B`、行距 `252 B` 上传字形，或 `copyTextureToBuffer` 将 `63 × 2` 的 RGBA8 区域写入容量恰为 `508 B`、目标偏移 `4 B`、每行 `252 B` 的紧凑缓冲）：
     - **`copyBufferToTexture`（缓冲 → 纹理）**：
       1. 满足设备与块字节对齐：直接录制 `CopyBufferToTextureRegion`；
       2. 不满足对齐且源为**不含 `COPY_DST` 的纯 `Upload` 映射缓冲**（CPU 映射内存为唯一权威源）：从 CPU 映射内存逐行提取子矩形交由 `RDGBuilder::UploadTexture` 对齐打包；
       3. 不满足对齐且源为**允许 GPU 写入的 `Device` 缓冲**（含 `MAP_WRITE | COPY_DST | COPY_SRC` 可写设备缓冲与纯设备缓冲）：在 GPU 上经字节寻址 `CopyBufferToBuffer` 逐行拷入瞬态对齐 RDG 缓冲后再执行 `CopyBufferToTextureRegion`。
     - **`copyTextureToBuffer`（纹理 → 缓冲，分流 `MAP_READ` 按槽暂存与 `Device` 同批 GPU 对齐中转）**：目标为 `MAP_READ` 缓冲时直接按设备对齐分配 `FrameSlot` 的 `slotReadbackStaging` 单次录制 `CopyTextureToBufferRegion` 并在批次完成后按 `CommandTape` 顺序紧凑发布至主机内存；目标为 `Device` `COPY_DST` 缓冲（后续命令可能在同一批次 GPU 上直接读取）时，满足设备偏移与行距对齐则直接录制 `CopyTextureToBufferRegion` 写入目标缓冲，**不满足偏移或行距对齐则在当前 RDG 时间线上先将源纹理区域 `CopyTextureToBufferRegion` 拷入瞬态对齐 `Device` 缓冲，再按行录制 `height` 次字节级 `CopyBufferToBuffer`（每次 `tightRowBytes`）紧凑写入目标 `Device` 缓冲的 `offset + row * tightRowBytes`**。
3. **批次状态化 `GpuFence`：Java 前置三态分支、与 `submit` 共享终态表面复位辅助入口及免 30 秒超时中止的 Native 等待循环**：
   - 每个录制批次持有轻量状态对象 `BatchSubmission`（`RECORDING`、`SUBMITTED(seq)`、`FAILED`），L1 终态失败的批次置为 `FAILED` 以隔离提交序号；
   - **`GpuFence.awaitCompletion(timeoutNS)` 完整三态契约**：
     - **`RECORDING` 或 `FAILED` 态（纯 Java 短路，零 Native 等待调用）**：若 `timeoutNS == 0L` 直接返回 `false`；若 `timeoutNS != 0L` 直接抛出 `IllegalStateException`（避免渲染线程无限等待自身尚未提交或已进入终态失败的批次）；
     - **仅 `SUBMITTED(seq)` 态**：先检查 Java 缓存已完成序号（若未满足则调用 `rn_wait_submit` 刷新已完成序号；**一旦确认 `completed >= seq`，在向调用方返回 `true` 前同步完成截至 `seq` 的已完成批次 `FrameSlot` 读回暂存 `InvalidateMappedRange`、按 `CommandTape` 顺序主机内存发布与回调排水**，保证等待 Fence 成功后立即调用 `mapBuffer` 或读取已打开只读视图必定看到最新字节）——因 `RadRay` 双后端 `Fence::Wait(seq)` 硬编码 `WaitFor(seq, 30000)` 并在非设备丢失超时后直接 `RADRAY_ABORT`，`rn_wait_submit` **严禁对 `GpuFence.NO_TIMEOUT`（`-1L`）直接调用 `Fence::Wait`**，且在每次轮询/等待后均同步检查 `device.IsDeviceLost()`：**一旦 `rn_wait_submit`（或 `rn_sync_query_pool`）首次检出设备丢失返回 `RN_STATUS_FAILED` + `RN_SUBMIT_FLAG_DEVICE_LOST`（如 `Minecraft` 帧头已执行 `windowSurface.acquireNextTexture()` 后，`MappableRingBuffer.currentBuffer()` 在 `rn_submit_frame` 之前等待旧 Fence 首次发现丢失），Java 侧必须走与 `rn_submit_frame` L1 终态完全同一个幂等清理入口 `enterTerminalFailure`——将设备标为 `poisoned`，经 `raynium.accesswidener` 同步将活跃 `FrontendGpuSurface` 的 `hasImageAcquired` 与 `hasBlittedTexture` 强制复位为 `false`，再抛出 `GpuDeviceLossException`**（防止退出时 `windowSurface.close()` 因表面仍处获取态抛错跳过 `RenderSystem.shutdownRenderer()`），其余正常等待情形统一规定为：
       1. `timeoutNS == 0L`：调用 `Fence::GetCompletedValue()` 刷新真实已完成序号（上游保证设备丢失时不伪造 `UINT64_MAX`）并立即返回 `completed >= seq`；
       2. `timeoutNS < 0L`（`NO_TIMEOUT`）：以有限切片（如每次 `1000 ms`）循环调用 `Fence::WaitFor(seq, 1000)`、检查 `!device.IsDeviceLost()` 并复查 `GetCompletedValue() >= seq` 直至完成；
       3. `timeoutNS > 0L`：使用无溢出商加余数换算总毫秒上限 `totalMs = (timeoutNS - 1L) / 1_000_000L + 1L`（对 `Long.MAX_VALUE` 安全无溢出），按单调时钟截止时间分段调用 `Fence::WaitFor(seq, min(remainingMs, 1000))`（期间检出 `IsDeviceLost()` 立即中断报错）直至完成或到达截止时间返回 `false`。

    - **恢复线性执行序：`BeginFrame()` → 全部可失败准备与分配（字节流/句柄校验 + `TerrainResidency` 更新 + `FlushMappedRange`）→ `AcquireNext()` → `RunFrame()` → `Present()`**，确保 `AcquireNext()` 与 `RunFrame() + Present()` 之间不存在任何因准备分配失败而遗留未消费 `SwapChainFrame` 的分支，并按三层边界处理故障（全程零跨子系统回滚）：

         - `RayniumCommandEncoder.submit()` 在封存 Tape 或进入 `rn_submit_frame` 之前检查 `isInRenderPass()`。若 Pass 仍打开，当场抛 `IllegalStateException`，保留当前 Pass、指令流和 `RECORDING` 批次。调用方可以关闭原 Pass 并提交同一批次。
      2. **第 2 层：L0 表面次优与可恢复异常（消费或跳过交换链 `output` Pass，返回 `RN_STATUS_OK` 且 `out_submit_sequence > 0`）**：
         - **已正常呈现但附带次优重配提示（`RN_PRESENTED_SUBOPTIMAL`）**：当 `AcquireNext(100)` 返回 `SwapChainStatus::Success` 且 `NativeStatusCode == VK_SUBOPTIMAL_KHR`（随后 `Present()` 返回 `Success`），或 `Present()` 返回 `NativeStatusCode == VK_SUBOPTIMAL_KHR` 时，本帧已真实完成交换链渲染与呈现（仅呈现一次），输出 `RN_PRESENTED_SUBOPTIMAL`；Java 仅将 `RayniumGpuSurfaceBackend.suboptimal` 置为 `true`（驱动下一帧 `Minecraft` 主循环帧头通过 `windowSurface.isSuboptimal()` 主动调用 `configure()`），**不缓存待抛 `SurfaceException`**（与原版 `VulkanGpuSurface` 对 `VK_SUBOPTIMAL_KHR` 仅置 `swapchainSuboptimal = true` 而不置 `eatenException` 严格一致）；
         - **过期重建、暂不可用或表面丢失（`RN_PRESENT_SKIPPED` / `RN_PRESENT_RECREATE` / `RN_PRESENT_SURFACE_LOST`）**：当窗口不可呈现，或 `AcquireNext(100)` 返回 `RetryLater`、`RequireRecreate`，或返回 `SwapChainStatus::Error` 但 `!device.IsDeviceLost()` 且 `NativeStatusCode == VK_ERROR_SURFACE_LOST_KHR` 时：**不中止本批工作，仅跳过末尾交换链 `output` 上屏 Pass，照常跑完离屏 `RunFrame()`**（`TerrainResidency` 共享四边形索引与顶点上传、离屏渲染、`ReadBack` 缓冲写入、时间戳查询、Fence 信号以及当批末尾待退役资源绑定 `seq` 全部真实上 GPU 完成）；若 `AcquireNext` 成功取帧且 `RunFrame()` 返回 `true`，随后 `Present()` 返回 `RetryLater`、`RequireRecreate`（非 `VK_SUBOPTIMAL_KHR`，如 `VK_ERROR_OUT_OF_DATE_KHR`）或非设备丢失的 `SURFACE_LOST`，同样按实际结果输出 `RN_PRESENT_SKIPPED`、`RN_PRESENT_RECREATE` 或 `RN_PRESENT_SURFACE_LOST`（纯离屏批次输出 `RN_PRESENT_NONE`，健康呈现输出 `RN_PRESENTED`）；
         - **遵守 `Minecraft` 主循环异常边界（绝不在 `submit()` 或 `present()` 抛受检 `SurfaceException`）**：Java 收到 `RN_STATUS_OK` 后正常登记 `BatchSubmission = SUBMITTED(seq)` 与全部在途寿命，`submit()` 与紧随其后的 `present()` 均正常返回，使 `FrontendGpuSurface.present()` 自然将 `hasImageAcquired` 清零；对 `RN_PRESENT_RECREATE` 与 `RN_PRESENT_SURFACE_LOST`，`RayniumGpuSurfaceBackend` 置 `suboptimal = true`（`SURFACE_LOST` 额外置 `needsNativeRecreate = true`）并缓存待抛 `SurfaceException`（同原版 `eatenException`）；下一帧帧头若调用方先执行 `configure()` 重建成功（常规 `RECREATE` 走排空后 `SwapChain::Recreate`；`SURFACE_LOST` 因底层 `VkSurfaceKHR` 已失效，走 `Finish + Queue::Wait` 后**销毁旧 `gpu::SwapChain` 并重新调用 `CreateSwapChain`**），则一并清空 `suboptimal`、`needsNativeRecreate` 与缓存异常；若未调 `configure()` 直接调用 `acquireNextTexture()`，则抛出缓存的 `SurfaceException` 交由帧头 `catch (SurfaceException)` 恢复；
      3. **第 3 层：L1 渲染器/设备终态故障（`poisoned` 终态，不回滚驻留表，严格区分 `out_submit_sequence == 0` 与 `> 0`）**：
         - 触发条件涵盖：① `BeginFrame()` 返回后检出 `device.IsDeviceLost()`；② `AcquireNext()` 之前的 Native 准备与分配失败（GPU 几何池 OOM 或损坏字节流，此时 `AcquireNext()` 调用次数严格为 `0`）；③ `AcquireNext()` 返回 `device.IsDeviceLost()` 或非 `SURFACE_LOST` 的致命错误（不调 `RunFrame()`）；④ `RunFrame()` 因 `device.IsDeviceLost() == true` 返回 `false`（覆盖 `Prepare` 首次创建瞬态纹理/缓冲、`Record` 命令缓冲开启/中途/闭合或 `Submit` 队列提交首次检出设备丢失；上游对 `!IsDeviceLost()` 的健康设备校验拒绝或必需资源 OOM 已在原处 `RADRAY_ABORT` fail-fast，`rn_submit_frame` 亦在调用上游丢失态 `DiscardAcquiredFrame` 注销已获取 `SwapChainFrame` 前显式校验 `device.IsDeviceLost()`，绝不在健康设备上进入弃帧路径）；⑤ `RunFrame()` 成功上队（`out_submit_sequence > 0`）后，`Present()` 检出 `device.IsDeviceLost()` 或返回除 `VK_ERROR_SURFACE_LOST_KHR` 之外的不可恢复 `SwapChainStatus::Error`（如 Present 内存耗尽）；
         - Native 行为：由 `ScopeGuard` 清空槽内指向当次调用栈/临时内存的借用视图；**当未完成队列提交（`out_submit_sequence == 0`，即条件 ①～④）时**，**严禁当场销毁当批携带的待退役资源**（统一保留在存活表内直至析构 `FrameScheduler::WaitIdle()` 排空另一在途槽后再集中释放，防止单次准备 OOM 时误杀前序在途槽仍在引用的资源，同时保留半开 `_slotBegun` 槽交由 `WaitIdle()` 按从旧到新顺序收尾命令缓冲并清理槽内对象）；**当队列已完成提交（`out_submit_sequence > 0`，即条件 ⑤）时**，当批 GPU 命令与待退役资源已真实绑定在途 `seq`，保持该槽正常提交绑定关系；随后统一将 `Renderer` 置为 `poisoned` 终态（后续一切提交/同步请求立即快速失败，确保 `Minecraft.emergencySave()` 内部 `setScreenAndShow` 重入渲染时无副作用快速返回），若 `device.IsDeviceLost()` 则置 `RN_SUBMIT_FLAG_DEVICE_LOST`，返回 `RN_STATUS_FAILED`；
         - Java 行为：**无论返回 `OK` 或 `FAILED`，永远先检查 `out_submit_sequence`——若 `out_submit_sequence > 0`（如条件 ⑤ `RunFrame` 已上队而 `Present` 致命报错），必须先将 `BatchSubmission` 标为 `SUBMITTED(seq)` 并正常登记当批全部在途缓冲、读回回调、查询与待退役寿命到 `seq`；仅当 `out_submit_sequence == 0` 时将 `BatchSubmission` 标为 `FAILED`**（关联该批次的查询槽与 `GpuFence` 自动按对应状态生效）；接着针对 `RN_STATUS_FAILED` 调用**与 `rn_wait_submit` / `rn_sync_query_pool` 共用的幂等终态入口 `enterTerminalFailure`——经 `raynium.accesswidener` 强制将活跃 `FrontendGpuSurface` 的 `hasImageAcquired` 与 `hasBlittedTexture` 复位为 `false`**（保证无论是 `submit` 期还是帧头 `acquireNextTexture` 后等待旧 Fence 首次发现丢失，测试回收或客户端退出执行 `windowSurface.close()` 均不会因获取态残留抛出二次异常跳过 `RenderSystem.shutdownRenderer()`），将 Java 侧渲染器标为 `poisoned` 并按 `RN_SUBMIT_FLAG_DEVICE_LOST` 抛出 **`GpuDeviceLossException`**（使客户端主循环正常写出 CrashReport 并执行 `emergencySave()` 同步保存单人世界存档）或 `IllegalStateException`，不再复用旧 `Renderer`；
  - **同步、按槽读回发布与查询池轮询入口**：分段循环等待且检出 `IsDeviceLost()` 即刻中断带出 `RN_SUBMIT_FLAG_DEVICE_LOST`（在 Java 侧同样走 `enterTerminalFailure` 复位活跃表面获取态）的 `rn_wait_submit(renderer, target_sequence, timeout_ns, out_completed_sequence, out_flags)`（内部对截至 `out_completed_sequence` 已完成批次的 `FrameSlot` 专属 `slotReadbackStaging` 执行一次 `InvalidateMappedRange`，并按 `CommandTape` 顺序将数据发布至目标 `MAP_READ` 主机内存）与 `rn_sync_query_pool`（对已完成 `FrameSlot` 查询读回缓冲执行 `InvalidateMappedRange`，仅将匹配逻辑槽最新提交序号的结果发布至 CPU 逻辑槽缓存）。

     3. **L1 渲染器/设备终态（含 `seq == 0`、`seq > 0`、`Prepare` 期设备丢失、帧头 `acquire` 后等待旧 Fence 丢失及真实 C ABI 销毁入口免超时 abort）与三态 `GpuFence`**：分别注入 ① `AcquireNext` 前准备失败（断言原生 `AcquireNext()` 调用次数严格为 `0`、返回 `(RN_STATUS_FAILED, 0, ...)`、前序在途槽仍在引用的当批待退役资源未提前销毁、活跃表面 `isAcquired()` 已经 `accesswidener` 复位、`Renderer` 进入 `poisoned` 拒绝后续重入提交且 `close()` 干净释放全部资源）、② **`RunFrame` 已成功上队（`out_submit_sequence > 0`）后 `Present` 返回不可恢复 `Error`（非 `SURFACE_LOST`）或 `DeviceLost`**（断言 Java 先按 `seq > 0` 将 `BatchSubmission` 标为 `SUBMITTED(seq)` 并登记在途资源/读回/待退役寿命，再复位 `isAcquired()`、置 `poisoned` 并抛出对应异常）、③ **在先成功提交至少一帧（使 Native `_submitted > 0` 且持有旧 `GpuFence`）并含已获取表面的场景下模拟全套 `DeviceLost` 发现点——覆盖 `BeginFrame`、`AcquireNext` 成功后 `Prepare` 首次创建瞬态纹理触发设备移除、`RunFrame` 提交期、`Present` 期，以及复刻 `Minecraft` 帧头顺序“先 `surface.acquireNextTexture()` 置获取态 → 尚未调用 `rn_submit_frame` 前在 `oldFence.awaitCompletion(NO_TIMEOUT)` 中由 `rn_wait_submit` 首次发现 `DeviceLost`”**（断言所有分支均立即跳出等待、经共用 `enterTerminalFailure` 将活跃 `FrontendGpuSurface` 的 `isAcquired()` 复位为 `false` 并抛出 `GpuDeviceLossException`，重入渲染尝试无副作用快速失败，**随后依次通过真实 `surface.close()` → `rn_destroy_swapchain` 与 `device.close()` → `rn_destroy_renderer` 退出，全程零 `Cannot close a surface while it is acquired` 异常、零 `Renderer::Finish` 5s 超时 `RADRAY_ABORT`、零死等、零验证层残留引用报错**）与 ④ **Native 侧死亡测试注入“健康设备 `AcquireNext` 成功后 `Submit` 触发 RHI 校验拒绝（`IsDeviceLost() == false`）”**（断言在调度器/提交点直接 fail-fast 中止，绝不误入仅允许丢失态调用的 `DiscardAcquiredFrame`）；验证 `RECORDING` 与 `FAILED` 两态下 `GpuFence` 的 `0` 超时返回 `false`、非零超时抛 `IllegalStateException` 且 Native 等待调用次数严格为 `0`，覆盖 `Long.MAX_VALUE` 防溢出正纳秒、分段等待超时恢复及同批先用后 `close()` 安全退役。
