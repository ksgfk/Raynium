2. 先确立句柄分配、单一 FIFO 工作队列与四阶段水位生命周期（前端内部 `last_enqueued_sequence` + 跨 ABI 回传三进度水位），可使后续 C++ SRP（`SrpShaderLibrary`、`ScriptableRenderer`、`VanillaRenderer` 及二期 `UniversalRenderer`）直接驻留于专用渲染线程内，保持 100% 单线程无锁实现。

### 0.2 为什么跨线程切分面必须设在 `FrameScheduler` 前端而非 `FramePipeline::Extract` 之后

核查 `external/RadRay` 源码确认以下三条不可违背的底层契约：

1. **RHI 全局单线程串行契约**：`RadRay` RHI 不支持跨线程并发 CPU 调用；同一个 `gpu::Device` 上的缓冲/纹理/查询池/着色器/PSO 创建与销毁、`CommandAllocator::Reset`、`UploadArena` 映射刷新、命令编码、`Queue::Submit`、`SwapChain::AcquireNext/Present` 及 `Fence` 操作必须由同一线程串行完成。
2. **`FrameScheduler` 与 `RenderGraphFramePipeline::Extract` 的真实职责**：
   - 上游 `FrameScheduler::RunFrame()` 在单线程内连续执行 `BeginFrame() → Extract → Prepare → Record → Submit`；其中 `BeginFrame()` 立即调用 `FrameSlot::ResetCommandStorage()` 重置底层 RHI `CommandAllocator` 与 `TransientParameterSetPool`；且 `RenderGraphFramePipeline::OnSlotCompleted(FrameSlot&)` 声明为 `final`；
   - `RenderGraphFramePipeline::Extract(slot)` 内部直接运行 `SetupGraph` 与 `RDGBuilder::Compile()`，其 `ImportPersistentBorrowed/Owned` 依赖读取**上一帧在 `Submit()` 末尾通过 `CommitSubmittedStates()` 才发布的持久资源终态（`GetSubmittedState()`）**。若第 $N$ 帧在渲染线程尚未完成 `Submit()`，主线程提前抢跑第 $N+1$ 帧的 `FramePipeline::Extract`，读到的持久纹理初态将失真。
3. **Raynium 混合架构下的等价切分点**：
   - 在 Raynium 中，动态游戏世界位于 MC Java 主线程（`Minecraft.renderFrame` → `GameRenderer.extract` → `GameRenderer.render` 命令与数据录制，MC 源码获取见 [阅读 Minecraft 源码](../guide/dev-environment.md#阅读-minecraft-源码)）。
   - **MC 主线程完成当帧命令流、上传流与地形视图准备并封包（`seal`）的时刻，即对应引擎级的“Extract 抽取并冻结只读快照”**；专用 Native 渲染线程接收冻结后的 `FramePacket`，独占 `DeviceContext` 按严格 FIFO 顺序执行资源变更、帧构建录制提交与交换链呈现。

## 2. 总体架构设计（三大统一不变量与 29 入口全量契约矩阵）

> 以下第 2～5 节为助手基于源码审计与十轮审校收敛的技术方案。所有新增 C++ 模块严守根 `AGENTS.md` 约束：禁止默认构造加 `Init` 二段式初始化（统一采用 `static bool Create` 准备完全部资源后构造有效对象），显式使用 `radray::` 容器与智能指针，C ABI 状态仅返回 `RN_STATUS_OK` / `RN_STATUS_FAILED`，健康设备内部契约违约使用 `RADRAY_ABORT`。

### 2.1 不变量一：单一严格 FIFO、快慢路径统一终态门禁与锁外屏障矩阵

主线程发往专用渲染线程的全部工作项进入同一个单向 FIFO 队列 `WorkerCommandQueue`，所有可能发生 RHI 分配/编译失败或需返回底层真实页号的操作均在确认底层分配成功后才交付有效句柄：

1. **三类 FIFO 队列元素**：
   - `ControlOp`（**100% 无 RHI 创建失败风险的流式数据与退役命令**）：`UploadTexture`、`RegisterPooledOrReadbackBuffer`（仅限纯 `MAP_READ` 或已命中 `MappedUploadPool`/`DeviceBufferPool` 既有 `GpuBuffer` 的登记及初始上传排入）、`CreateQueryPool`（纯内存槽表）、`DestroyTexture`、`DestroyBuffer`、`DestroyPipeline`、`DestroyQueryPool`、`RemoveStaticMesh`；
   - `FramePacket`：一帧完整提交包（未消费帧槽上限 `1` 批，满槽时回压主线程）；
   - `BarrierTask`：携带 `{ rn_status status; bool done; }` 的同步屏障——包含**会话与全部冷路径可失败 RHI 分配屏障（`InitEnv`、`CreateRuntime`、`CreateRenderer`、`CreateTexture`、`RegisterPipeline`、池未命中的冷路径 `CreateBuffer`/`CreateMappedBuffer`、稳态帧 0 次的 `UpsertStaticMesh`）**、**交换链操作屏障（`CreateSwapchain`、`ResizeSwapchain`）**、**排空屏障（`FlushRenderer`）**与**销毁屏障（`DestroySwapchain`、`DestroyRenderer`、`DestroyRuntime`、`DestroyEnv`）**。
2. **铁律：所有 RHI 操作与对象创建/析构 100% 在状态锁之外执行，且快慢创建路径统一检查终态**：
   - **前置会话保护**：重复 `rn_init_env`、跨线程或存在活跃 `runtime` 的 `rn_destroy_env` 在投递屏障前立即返回 `RN_STATUS_FAILED`，绝不触碰或 `join` 原属主活跃会话；仅本次新起的 worker 握手失败或合法 `rn_destroy_env` 完成锁外析构退出后，主线程泵消息并执行 **`workerThread.join()`**；
   - **前端快速创建路径与排队屏障的双端终态门禁**：① 主线程在分配 ID、从 `MappedUploadPool`/`DeviceBufferPool` 取缓冲或登记 `rn_create_query_pool` 存活位的**同一把状态锁内**，必先检查 `!enqueue_closed && !host_fault_requested && terminal_flags == 0`，若已处终态立即返回 `RN_STATUS_FAILED`（不分配新句柄、不取池对象）；② Worker 取出归属某 `rn_renderer` 的**任何非销毁类 `BarrierTask`** 时，同样先检终态——若前一帧已触发终态，绝不调用底层创建或缩放，保持输出为空，直接置 `status = RN_STATUS_FAILED, done = true` 唤醒主线程；
   - **正常态创建失败隔离**：健康 `renderer` 下 `CreateRuntime`、`CreateRenderer`、`CreateTexture`、`RegisterPipeline`、冷路径 `CreateBuffer`/`CreateMappedBuffer`、`UpsertStaticMesh` 若因格式不支持、坏 `.rnsp` 或分配失败返回 `false`（且 `!device.IsDeviceLost()`），仅令当次屏障返回 `RN_STATUS_FAILED` 而不毒化上层会话或当前 `renderer`；
   - **`FlushRenderer`、`ResizeSwapchain`、`DestroySwapchain` 完整排空、缩放/重建失败统一待重建态与单参销毁契约**：三者在锁外统一执行 **`Renderer::Finish()` + `FrameScheduler::WaitIdle()` + `Runtime().GetQueue().Wait()`** 排空在途 `Present`；`FlushRenderer` 随后强制复查 **`!renderer.IsTerminal() && !device.IsDeviceLost() && completed_sequence >= target`** 并写回 `rn_wait_result`（等待期丢设备则转终态结算并置 `RN_STATUS_FAILED`）；`ResizeSwapchain` 排空后先校验描述符与相同 `hwnd`（非法直接返回 `RN_STATUS_FAILED` 且不触碰现有 `_chain`），通过校验后若同代为 `RN_PRESENT_SURFACE_LOST` 或 `_chain == nullptr` 则重置旧 `_chain` 并调 `CreateSwapChain`，否则调常规 `_chain->Recreate`——**无论 `Recreate` 还是 `CreateSwapChain` 返回 `false`（因 Vulkan `Recreate` 已退役旧链、D3D12 `Recreate` 已清空 `_frames`），均先复查 `device.IsDeviceLost()`：丢设备则转终态结算，设备健康则统一执行 `_chain.reset()`（置 `_chain = nullptr`）、保留 `_hwnd` 并置 `surface_recovery_state = RN_PRESENT_SURFACE_LOST` 返回 `RN_STATUS_FAILED`**（此后针对该句柄的上屏提交免解引用跳过 `AcquireNext`/`Present`、照常执行离屏工作并报 `RN_PRESENT_SURFACE_LOST`，后续 `rn_resize_swapchain` 自动走 `CreateSwapChain` 重试恢复，`rn_destroy_swapchain(rn_swapchain*)` 保持单句柄参数签名安全释放外层句柄并返回 `RN_STATUS_OK`）；`CreateSwapchain` 与成功的 `ResizeSwapchain` 统一推进 `surface_generation++` 并清零同代 `surface_recovery_state = NONE(0)`；
   - **销毁屏障（`DestroySwapchain`、`DestroyRenderer`、`DestroyRuntime`）**：均维持单句柄参数签名（无 `rn_wait_result*` 输出），无论正常态、待重建态（`_chain == nullptr`）或终态均在锁外完成对象析构后置 `RN_STATUS_OK`。

### 2.2 不变量二：两阶段锁内结果发布、防重入终态只读访问、`ENQUEUED` Fence 与 `MAP_READ` 发布

1. **`rn_submit_frame` 可恢复入口校验与不可恢复预检失败的四步终态交接**：
   - ⓪ **C ABI 入口参数门禁（可恢复，不毒化 `renderer`）**：保持与现有 [bridge.cpp](../../native/src/bridge.cpp) 一致的边界——对 `!result`、`!Owner(renderer)`、`!batch`、`batch->struct_size != sizeof(*batch)` 或 `batch->surface && batch->surface != renderer->swapchain`，主线程**绝不置 `host_fault_requested` 或 `enqueue_closed`**，直接在入口返回 `RN_STATUS_FAILED`（`result` 非空且属主合法时写出 `sequence = 0` 与当前快照），同一 `renderer` 后续合法提交仍正常成功；
   - ① **批次负载/命令预检失败锁内请求停止（不可恢复）**：通过入口门禁后，若 `batch` 内部标志/保留字/指针计数或视图/命令流预检非法（如非法 `opcode`），主线程**不将失败批入队、不分配 `sequence`**，回滚本批临时截图预留与查询槽修改，在状态锁内置 `enqueue_closed = true` 与 `host_fault_requested = true`，触发 `wakeEvent` 唤醒可能空闲的 worker，随后调 `WaitRenderSignal` 等待 `snapshot.flags != 0`；
   - ② **Worker 尾批读回采集 + 单次状态锁内原子发布终态（严格只发布已完整落地水位）**：worker 停止读取后续输入后，复用 2.2.3 的统一两阶段发布路径——**先在锁外**调 `_completion->GetCompletedValue()` 并在调用后**立即复查 `!device.IsDeviceLost()`**（因 D3D12/Vulkan `GetCompletedValue()` 内部会首次检测并标记丢设备同时返回旧缓存值），仅当设备仍健康时按提交序逐批（`s = _completed + 1 .. finalDone`）将时间戳、`FrameReadbacks` 与 `AsyncReadbackQueue::Poll`（`Map` + `InvalidateMappedRange` + 像素拷出 + `Unmap`）拷入 worker 私有结果缓冲；一旦任一批 `Map`/`Poll` 失败或中途发现 `device.IsDeviceLost()`，立即丢弃该批半成品并将安全完成水位 `safeDone` 定格在**全部必需读回均已成功的最高连续批次 `s - 1`**；**随后在同一次状态锁内**：将 `<= safeDone` 私有结果原子迁入 `CaptureRegistry` `Ready` 表、复核 `slot.sequence == s` 写入 `PublishedQueryPool`、挂入待同步 `MAP_READ` 队列并置 `completed_sequence = _completed = safeDone`；同时置 `enqueue_closed = true`、移除未执行 `FramePacket` 与非销毁 `ControlOp`（保留 `BarrierTask` 与销毁 `ControlOp`）、**仅撤销 `> safeDone` 的 `CaptureRegistry` `Pending` 请求**、置 `consumed_sequence = last_enqueued_sequence`、定格 `submitted_sequence`、写入 `flags`（`RN_SUBMIT_FLAG_TERMINAL_ERROR = 2u`，`device.IsDeviceLost()` 叠加 `RN_SUBMIT_FLAG_DEVICE_LOST = 1u`）并广播唤醒事件；
   - ③ **主线程同步读回并返回**：主线程从 `WaitRenderSignal` 醒来，执行 `SyncFrontendReadbacks(snapshot.completed_sequence)`，写出 `rn_submit_result{ .sequence = 0, .progress = snapshot }` 并返回 `RN_STATUS_FAILED`；
   - ④ **保证**：既不死等也不悬空第 $N-1$ 批内存，且凡 `completed_sequence >= N`，批次 $N$ 的截图、查询与 `MAP_READ` 必已完整落入锁保护的前端可读结构。
2. **正序号入队绑定 `ENQUEUED(seq)` Fence、正常批次 `consumed_sequence` 发布点与防重入逐回调异常隔离**：
   - `RayniumCommandEncoderBackend.submit()` 在 `memory.seal(submitting)` 后**立即先切新 `CommandTape`**（`T1` 起生效），再调 `submitting.submit(measuring)`；
   - **入队返回时（`sequence > 0`）**：[BatchSubmission.java](../../src/client/java/dev/raynium/client/renderpearl/BatchSubmission.java) 状态机扩展为 `RECORDING → ENQUEUED(seq) → FAILED`——正序号入队时**立即调用 `submission.enqueued(seq)` 绑定可等待序号**（使 [RayniumGpuDeviceBackend.java](../../src/client/java/dev/raynium/client/renderpearl/RayniumGpuDeviceBackend.java) `getTimestampCalibrationOffset()` 等在 `submit()` 后立刻调 `fence.awaitCompletion(-1)` 能直接携 `seq` 进入 `rn_wait_submit`，且 [RayniumQueryPool.java](../../src/client/java/dev/raynium/client/renderpearl/RayniumQueryPool.java) 立即可用 `submission.sequence()` 匹配查询进度），同时登记进 `NativeRenderer` 在途队列并对上屏批置 `submittedBlit = true`；**`onSubmitted` 回调此时不执行**；`sequence == 0` 时调 `submission.failed()`、`releaseAcquisition()` 与地形未入队回滚（`T1` 即生效）；
   - **队列腾位与正常批次 `consumed_sequence` 发布点分离**：worker 从 `WorkerCommandQueue` 弹出 `FramePacket(seq)` 时仅递减 `queued_frames`（腾出 `1` 批回压槽位供主线程并发录制入队下一批），**绝不在出队或 `CommandTape::Decode` 返回时推进 `consumed_sequence`**（因 `Decode` 与 `TerrainResidency::PrepareFrame` 保留的 `BorrowedBytes` span 直至 `CompiledRDG::Prepare` 的 `FillUploads` 才拷入 `UploadArena`）；正常批次统一在 **`FrameScheduler::RunFrame()` 完成且 `_pipeline->ClearInput()` 清空输入指针后（`SwapChain::Present` 之前）**于同一次状态锁内推进 `consumed_sequence = seq` 与 `submitted_sequence = seq`；
   - **进度与终态派发时（`syncWorkerState(snapshot)` 前置标记 `terminalSettling` 与逐回调异常隔离）**：① **若 `snapshot.flags != 0`，在派发首个回调之前立即置 `terminalSettling = true`**（同时被 `checkOpen()` 视为已进入终态以拒绝嵌套新提交/创建，并令嵌套只读查询直接返回已发布数据而不重入 `syncWorkerState`）；先回收 `<= consumed_sequence` 借用输入，按 **`presented_frames` 增量（`snapshot.presented_frames - lastObservedPresentedFrames`）**推进 `BenchmarkSession` 呈现帧计数；② 对 `<= submitted_sequence` 的 `onSubmitted` 回调与 `<= completed_sequence` 的 `onCompleted` 回调，**逐个按“先从队列弹出、再单独 `try / catch (Throwable)` 执行”**（已完成 `<= completed_sequence` 的 `BatchSubmission` 保留原正序号以支撑查询匹配，异常按首发记录、后续 `addSuppressed` 累积）；③ 最外层 `finally` 块在 `snapshot.flags != 0` 时幂等取消剩余未达成回调、仅将 `> completed_sequence` 未完成在途 `BatchSubmission` 置 `FAILED`（清零其序号）、回收剩余借用输入、置 `poisoned = true` 并调 `releaseAcquisition()`，**最后由最外层统一抛出累积的回调 `Throwable` 或终态异常**。
3. **正常/终态共用的“锁外采集 + 锁内发布”协议、全量已发布结果只读路径（截图/查询/`MAP_READ`）与四快照入口**：
   - **统一两阶段完成发布（杜绝共享表数据竞争）**：正常推进与终态尾批共用同一套流程——① **锁外 RHI 采集**：worker 在锁外采样 `_completion->GetCompletedValue()` 并复查 `!device.IsDeviceLost()`，逐批将已完成的时间戳、截图像素与 `FrameReadbacks` 拷入 worker 私有结果缓冲（任一批读回 `Map` 失败即停在 `s - 1` 并转入终态结算）；② **单次状态锁内原子发布**：在同一把状态锁保护下完成 `CaptureRegistry` `Pending → Ready` 迁移、复核 `slot.sequence == s` 写入 `PublishedQueryPool`、挂入待同步 `MAP_READ` 并更新 `completed_sequence`；
   - **覆盖全部三类读回原语的终态派发期与终态后只读访问**：[NativeRenderer.java](../../src/client/java/dev/raynium/bridge/NativeRenderer.java) 对 `submitFrame`、`pollCompleted`、`awaitSubmission`、`flush`、`NativeBuffer.map(write=true)` 及全部创建/上传入口维持 `checkOpen()`（`poisoned || terminalSettling` 时立即抛 `IllegalStateException`）；对全部已发布结果只读入口统一走仅检属主线程与未关闭句柄的 **`checkAlive()`**：① `pollCapture(id)` 直接读 `Ready` 表；② `syncQueryPool`（`RayniumQueryPool.getValue`/`getValues`）在 `terminalSettling || poisoned` 时**跳过重入 `syncWorkerState`** 直接返回已发布样本（仅在 `!terminalSettling && !poisoned && snapshot.flags != 0` 首次外部观察时进入 `syncWorkerState`）；③ **[NativeBuffer.java](../../src/client/java/dev/raynium/bridge/NativeBuffer.java) `map(offset, length, read=true, write=false)`** 校验 `owner.checkAlive()`、缓冲未关闭、属主一致、`USAGE_MAP_READ` 与合法区间，仅在 `!owner.isTerminalSettling() && !owner.isPoisoned()` 时调 `owner.pollCompleted()`，在终态派发回调内或捕获终态异常后**跳过 `pollCompleted()` 直接基于已由 `SyncFrontendReadbacks(safeDone)` 同步完毕的 `frontendHost` 打开只读 `MappedView`**；④ `drainTelemetry()` 同样经 `checkAlive()` 弹出已退休遥测；
   - **唯一回传 `rn_wait_result` 的四个入口**：仅 **`rn_submit_frame`（内嵌 `progress`）、`rn_wait_submit`、`rn_sync_query_pool`、`rn_flush_renderer`** 写回最新 `rn_wait_result` 快照并在返回前统一执行 `SyncFrontendReadbacks(completed_sequence)` 拷入 `frontendHost`（`rn_destroy_swapchain` 保持单句柄参数不回传快照）；同一 `surface_generation` 内 `surface_recovery_state` 按 `NONE(0) < SUBOPTIMAL(4) < RECREATE(2) < SURFACE_LOST(5)` 单调锁存（仅匹配前端当前已配置代数时生效）；Java `renderer.flush()` 调 `rn_flush_renderer(handle, waitResult)` 后经 `syncWorkerState(snapshot)` 应用最新快照并返回已定格的 `last_present_outcome`。

### 2.3 不变量三：按等待语义区分完成条件的 `WaitRenderSignal` 与上界校验

主线程所有阻塞点统一经无锁泵送 `QS_SENDMESSAGE` 的 `WaitRenderSignal` 等待：`BarrierTask` 等 `task.done`；`rn_wait_submit` 先锁内校验 `sequence <= last_enqueued_sequence`（超界立即返回 `RN_STATUS_FAILED`），合法序号等 `completed_sequence >= sequence || terminal_flags != 0`（或超时）；满槽回压等 `queued_frames == 0 || terminal_flags != 0`；空闲期 worker 短周期自主推进 `Fence`。

## 3. 零拷贝所有权边界、缓冲双端存储、地形回滚与容错保序遥测详设

### 3.1 全覆盖围栏轮转零拷贝快轨（`RN_BUFFER_FENCE_ROTATED`）、普通 `MAP_WRITE` 存储与三层防绕过借用

1. **四类缓冲的精确存储、初始数据、Vulkan 映射刷新与池化返回地址契约**：
   - **`RN_BUFFER_FENCE_ROTATED`（不含 `COPY_DST` 的三处硬件围栏源：`RayniumTransientMemory`、`MappableRingBuffer`、`StagedVertexBuffer.GpuBufferPool` `usage = 22`）**：优先锁内取 `(usage, size)` **`MappedUploadPool`**（`completed_sequence >= retire_sequence`，预热 `512 KiB` 块），未命中走同步 `CreateMappedBuffer` 屏障创建持久映射 `MemoryType::Upload` 缓冲，冷热路径均返回非零 `upload` 映射地址，稳态零 CPU 字节重拷；**为满足非 host-coherent Vulkan `Upload` 内存可见性且严守 RHI 单线程契约**：① `initial != nullptr` 时，冷路径在屏障内、池命中路径通过 `RegisterPooledOrReadbackBuffer` `ControlOp`（排在后续一切 `FramePacket` 之前）由 worker 在首次 GPU 读取前执行 `upload->FlushMappedRange({0, size})`（覆盖池命中带 `initial` 创建后从未 `map` 即直接用作拷贝/绑定源的场景）；② 后续每批提交前，worker 按 `FramePacket` 固定的 `dirty_ranges` 对该类缓冲执行 `upload->FlushMappedRange({offset, length})`；
   - **未带 `RN_BUFFER_FENCE_ROTATED` 且不含 `COPY_DST` 的普通纯 `MAP_WRITE`（如单测 `MAP_WRITE | COPY_SRC`）**：由“CPU `HostShadowBuffer`（提供返回给 Java 的非空 `mapped` 地址）+ 底层 GPU `device` 缓冲（`CopyDestination | gpuUses`，供 `BufferEntry::Import` 读取）”组成；底层 `device` 缓冲优先锁内复用 `(gpuUses, size)` **`DeviceBufferPool`** 既有缓冲，池未命中时走同步 `CreateBuffer` 屏障确认 GPU 缓冲分配成功，**冷路径与池命中路径一律返回 `{id, 0, shadowHost}`（`mapped != nullptr`，确保 `NativeBuffer` 走持久写映射而不误调要求 `COPY_DST` 的 `writeBuffer`）**；**当 `initial != nullptr` 时，除拷入 `shadowHost` 外同步排入首次 `[0, size)` GPU 上传（先于后续批次脏区间上传执行）**，覆盖创建后从未 `map` 直接用作 `copyBuffer`/`bufferToTexture`/着色器源的合法路径；后续每批提交前将脏区间快照进 `FramePacket` 由 worker 经 RDG `UploadBuffer` + `MarkOutput` 上传；
   - **纯设备缓冲与 `MAP_WRITE | COPY_DST`**：无 `HostShadowBuffer`，冷路径（`CreateBuffer` 屏障）与池命中（`DeviceBufferPool` 免屏障）**一律返回 `mapped = nullptr`**（`initial != nullptr` 时排入初始 GPU 上传）；`MAP_WRITE | COPY_DST` 关视图时录内联 `WriteBufferBytes`；
   - **`MAP_READ`（可含 `COPY_DST`）**：锁内检终态后分配前端 `frontendHost`（`initial != nullptr` 时拷入初始字节）并返回非空映射地址，GPU 暂存由每帧槽 `FrameReadbacks` 按需管理。
2. **三层防绕过内存借用门禁（借用期严格持续至 `RunFrame` 完成后的 `consumed_sequence`）**：
   - **第一层**：`batchDesc`（96 B）、`viewRecords`（`280 B * view_count`）与 `dirtyRanges`（`24 B * dirty_count`）始终在 `rn_submit_frame` 返回前按值拷入 `FramePacket`；
   - **第二层**：仅当 `CommandTape` 绑定编码器回收池且全部视图经包内受控 `addPooledView`（校验 `storage` 由当前 `CommandTape.acquireViewStorage()` 分配并直接从其内部冻结描述符）添加时才置 `RN_BATCH_BORROW_POOLED`；调用公共 `addView(storage, parameters, ...)` 一律不置该位并在返回前完整深拷贝；
   - **第三层**：公共 `meshDirect`/`indexDirect` 立即拷入自有存储；仅 `RetainedTerrain` 受控路径登记持有至 `>= consumed_sequence`（即 worker 完成 `RunFrame` 消费全部 `BorrowedBytes` 之后）才释放的 `DirectUploadPool` 段执行零拷贝借用。

### 3.2 控制命令同步校验与撤销 `stageCommit` 的地形未入队回滚

1. **同步校验与终态一致性**：所有前端快轨入口在分配句柄/取池的同一把锁内检查终态；冷路径可失败 RHI 分配走同步 `BarrierTask`；`rn_remove_model_mesh` 对 `>= 16` 保持幂等成功，四个严格 `rn_destroy_*` 对未知/重复销毁返回 `RN_STATUS_FAILED`。
2. **撤销 `stageCommit()` 驻留变更的地形未入队回滚（`T1` 起生效）**：
   - `RetainedTerrain.capture()` 在录制期逐视图调用 `TerrainResidency.stageCommit()`（清空 `pendingSlotAllocs` 并提前写入 `uploadedEpoch`、`residentBySection`、`residentCount`、`uploadedIndices` 及驱逐槽回收），以支持同一 `CommandTape` 内多视图共享槽号；
   - 当 `CommandTape` 未入队即 `close()` 或 `rn_submit_frame` 预检失败返回 `sequence == 0` 时，按录制视图**逆序**执行 `ViewTransition.rollback()`：① 对本视图新暂存区块（`staged`），恢复 `p.uploadedEpoch = 0`、退回新分配 `layer.slotId` 至 `freeSlots` 并清零 `slotId`、将 `residentBySection[p.sectionKey]` 恢复为覆盖前旧驻留项（无旧项则移除）并递减 `residentCount`；② 对透明索引更新（`indexUploads`），将 `section.uploadedIndices` 恢复为更新前快照并重入 `TerrainCapture.recordDirtyIndices(section)`；③ 对本视图驱逐区块（`evicting`），从 `freeSlots` 收回并恢复原 `layer.slotId`、恢复 `p.uploadedEpoch = epoch` 与原 `uploadedIndices`、写回 `residentBySection`、递增 `residentCount` 并将 `p` 放回 `pendingRemovals`；④ **保留全部 `MeshPayload` 顶点与索引缓冲不释放**，强制置 `lastFrameCommitted = false`、`lastInstancesCommitted = false`、`capture.checkedResidencyEpoch = 0`，确保下一帧必定重扫并重录新区块上传。

### 3.3 两阶段截图/查询发布、整行完备 GPU 帧计时与 `Throwable` 安全基准收尾

1. **截图与查询槽全周期锁保护**：`rn_submit_frame` 在状态锁内校验 `Pending ∪ Ready` 全集 ID 唯一性与 `4096` 上限并原子写入 `Pending` 及失效重写查询槽；worker 锁外完成 RHI 读回拷入私有缓冲（遇 `GetCompletedValue()` 标丢设备或任一读回 `Map` 失败即停在上一完整成功批次），再在**同一把状态锁内**完成 `Pending → Ready` 迁移、复核 `slot.sequence` 写查询结果并推进 `completed_sequence`。
2. **抗 `WaitIdle` 反序回收、剔除混合缺样帧 GPU 样本且 `Throwable` 全覆盖的遥测与收尾链路**：
   - 上游 `RenderGraphFramePipeline::OnSlotCompleted(slot)` 在未开启计时（预热期 `!measure`）、校准无效或时间戳读回缓冲映射失败时会直接返回而不触发 `OnGpuTimingCompleted`。为此 worker 在每次槽位回收完成点（`BeginFrame()` 返回后对应槽的上一在途批次，以及 `WaitIdle()` 返回后全部槽的上一在途批次，此时 `OnSlotCompleted` 已执行完毕）调用 **`TelemetryTracker::FinalizeSlotBatch(seq)`**：① 未测量批标为 `unmeasured_done`；② 已收到 `OnGpuTimingCompleted`（按 `snapshot.UserSequence` 对号入座写入**该单批** `snapshot.TotalNanoseconds`）标为 `measured_with_gpu`；③ 测量批未收到回调标为 **`measured_missing_gpu`**；
   - **移除 C++ `target != nullptr`（`endsFrame`）跨批累加假设**：`TelemetryTracker` 沿连续递增 **`next_retire_sequence = 1, 2, ...`** 推进，跨过 `unmeasured_done`，对每个已完结测量批按提交序直接产出**单批粒度**的 `rn_batch_telemetry`（`measured_with_gpu` 置 `RN_TELEMETRY_HAS_GPU_NS` 并填该批 `gpu_ns`，`measured_missing_gpu` 清零该位并置 `gpu_ns = 0`），避免全离屏 Java 帧因无 `surface != nullptr` 批次而把 GPU 耗时滞留并入下一上屏帧；
   - **Java 侧整行完备性判定与 `Throwable` 安全 `finish()` 清理路径**：[BenchmarkSession.java](../../src/client/java/dev/raynium/client/benchmark/BenchmarkSession.java) 在测量帧提交批次返回 `sequence > 0` 时，**当场累加当帧 `javaPrepareNs`（列 `4`）与 `nativeCallNs`（列 `5`）**（同步等待计入列 `22` `nativeSyncWaitNs`），**登记 `sequence → currentRowIndex` 并递增 `expectedBatches[currentRowIndex]`**；`afterFrame()` 先写出该帧行（列 `6..21` 填 `-1` 占位并封口 `currentRowIndex < measurements.frameCount()`）。每条排出的 `rn_batch_telemetry` 按 `sequence` 查回 `rowIndex`：始终回填 CPU/统计列 `6..21`（列 `6..18` 累加、列 `19..21` 取该行末批，保留列 `0..5, 22`），递增 `receivedBatches[rowIndex]`，且当 `(flags & RN_TELEMETRY_HAS_GPU_NS) != 0` 时累加 `rowGpuNs[rowIndex]`、否则置 `rowMissingGpu[rowIndex] = true`——**严格仅当该行已由 `afterFrame()` 封口、`receivedBatches[rowIndex] == expectedBatches[rowIndex] > 0` 且 `!rowMissingGpu[rowIndex]`（即该帧全部预期批次到齐且每批均含有效 `RN_TELEMETRY_HAS_GPU_NS`）时，才向 `measurements.gpu(...)` 追加一次完整帧 `rowGpuNs[rowIndex]`**（任一批缺样则该帧不追加 GPU 样本，杜绝半帧残缺耗时污染 `gpu.csv`）。在 **`BenchmarkSession.finish()`（及 `tick()` 外层异常捕获）**中：原版对照组（`RenderMode.REFERENCE` 或无活跃未关闭 `NativeRenderer`）直接跳过排空；存在未关闭 Raynium `renderer` 时，将 `!renderer.isPoisoned()` 下的 `renderer.flush()` 与走 `checkAlive()` 的 `renderer.drainTelemetry()` 分别置于**捕获全量 `Throwable`（含完成回调抛出的 `Error` 如 `AssertionError`）**的保护块内记录失败、降级 `status = "failed"` 并保留原始异常，而将 **`measurements.finish(directory)`、`client-result.json` 写出与 `client.stop()` 置于覆盖 `flush`/`drain` 的 `finally` 必达清理路径**，完成后再按需重抛捕获到的 `Error`。

## 5. 阶段全绿递进实施路线（`T1`～`T3`）与可判定验收标准

> **里程碑划分准则**：首次允许 `rn_submit_frame` 异步提前返回的 **`T1`** 即完整冻结 ABI 23 四重门禁、29 个导出符号与 `48 / 56 / 152 B` 全部结构体布局，落地可恢复入口参数校验与不可恢复终态交接（锁外读回采集 + 读回失败截断水位 + 锁内原子发布 + 派发前 `terminalSettling` 防重入 + 截图/查询/`MAP_READ` 终态只读访问）、`Recreate`/`CreateSwapChain` 失败统一待重建态的 `ResizeSwapchain`、提交前切带、入队绑定 `ENQUEUED(seq)` Fence、`RunFrame` 后推进 `consumed_sequence`、撤销 `stageCommit()` 的地形回滚、`flush` 快照同步与 `presented_frames` 增量计帧、**100% 默认深拷贝**及迁移后的双后端故障测试桩/层，确保 `T1` 独立落地即 100% 全绿；**`T2`** 开启零拷贝快轨（含 `FlushMappedRange` 全覆盖）与防绕过池化借用；**`T3`** 完成按 Java 帧行完备性聚合单批指标及 `Throwable` 安全收尾的遥测链路、86 场景视觉与 6 场景基准收口。
