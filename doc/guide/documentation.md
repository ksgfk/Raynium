# 文档维护

## 归属

继续使用 `doc/`，不建立平行的 `docs/`。长期知识包含根 [AGENTS.md](../../AGENTS.md)、
`doc/architecture/` 和 `doc/guide/`；README 是项目介绍与入口，Git 保存历史版本。

| 位置 | 维护内容 |
| --- | --- |
| 根 AGENTS | 跨任务约束与按需阅读入口 |
| 根 README | 项目介绍、能力边界与少量入口 |
| architecture/overview | 当前实现地图、能力边界、完整文档与历史索引 |
| architecture 所属页面 | 已实现接口、职责、所有权、生命周期和有来源的源码事实 |
| guide | 环境、依赖、构建、测试、使用与文档维护方法 |
| `.agents/skills/` | 项目工作流程，不承载第二份工程契约 |
| `doc/history/` | 经用户授权保存的目标变化、设计思考、建议、设想、推断、方案、计划及历史快照，不作为当前契约 |

具体主题归属见[架构地图](../architecture/overview.md)。同一事实只维护一处，其余给摘要和链接。
术语在所属页面首次使用处解释，必要理由紧邻约束；不另建全局词汇表、编号决策、研究档案或计划目录。
现有 MC 与模组源码参考是有明确版本的接入证据，不代表本项目能力，也不自动扩大为持续外部研究。

## 事实边界

除 `doc/history/` 外，仓库文档只记录事实。是否出现“建议”一词不是判断标准：
尚不存在的模块、字段、调用时序或验收计划，即使用“负责”“必须”“首版”等确定语气书写，也属于方案。
用户确认一个目标或设计不等于它已经实现；确认过但尚未落地的内容仍只放 history。

| 内容 | 归属与证据 |
| --- | --- |
| 当前实现与缺失能力 | 当前页面；由源码、配置和锁文件支撑，缺失能力只描述现状 |
| 已执行验证 | 当前验证摘要或历史；写明日期、版本或源码状态、环境、命令、结果和范围 |
| 外部源码/API 事实 | 所属参考页面；注明版本或调查日期、仓库与源码路径、类和方法或规范来源 |
| 生效的仓库约束、工具操作步骤 | AGENTS、技能或操作指南；区分已生效规则与未实施的功能设计 |
| 目标、建议、设想、推断、候选接口、未来模块职责、实施路线和验收计划 | 仅 history；注明来源、当时确认程度及未实现范围 |

实现与验证是两条独立信息。DLL 加载、设备创建、测试通过、客户端启动、进入世界与渲染接管不能互相替代。
不因设备会话已实现就把资源、管线或整个阶段标为完成。第三方源码的能力也不属于 Raynium 已实现能力。
事实和方案混合时逐段拆分：有证据的部分留在当前页面，设计推演迁入历史，不能只去掉措辞而保留未来契约。
当前页面不设“提案”“下一步”“已确认未实现设计”专区，也不通过转述“文档建议”绕过这一边界。
实现落地后根据源码更新当前页面，历史快照保持原样。

## 页面与引用

每个 `doc/` Markdown 页面使用以下三行头部；根 AGENTS、README 和 SKILL 按各自用途组织。

```markdown
> - 适用: 什么任务需要读本文
> - 权威: 本文负责什么，相关内容由哪里维护
> - 锚点: `存在的仓库相对路径`
```

- 文档主要用中文，文件名使用小写英文与连字符，版本专属页面可含版本号。
- 锚点相对仓库根，指向已跟踪或待提交的实际文件；可使用 glob，不指向个人配置、忽略缓存或外部 checkout。
- Markdown 本地链接相对当前文档。代码用文件及类/方法定位，行号仅作辅助。
- 除非用户明确要求，文档（含 history）不保存 Git hash，包括完整值、缩写、表格和链接 URL 中的值。归档、验证或源码引用本身不构成保存授权；用日期、版本、来源路径和状态说明背景。
- RadRay 契约由上游维护；本项目只解释消费边界。精确依赖版本由 `native/radray.lock.json` 维护，不复制到文档；升级时核对引用仍适用。
- MC 源码参考注明 MC 版本、命名基线和类/方法，并链接[生成源码方法](dev-environment.md#阅读-minecraft-源码)。缓存路径可作为文字说明，不作为唯一证据或本地可点击链接。
- 第三方调查记录日期、版本、仓库和源码路径；未获保存 hash 的明确要求时，使用仓库入口和路径定位，不将浮动链接声称为调查时的固定源码。当前页面仅保留源码事实，推断和选型讨论归 history。整理不表示重新验证了外部行为。
- 代码注释描述 API 契约与局部不变量，文件头至多保留一个所属文档入口；设计正文由文档引用代码。

## 操作与验证

命令注明工作目录、工具、配置、依赖前提和预期产物。显式区分 fetch、第三方包准备、configure、build、test、运行与打包。
版本以 `gradle.properties`、Wrapper、CMake presets 和 RadRay 锁文件为准，避免在多个入口重复维护版本表。

验证摘要放在对应操作指南，标明日期、版本或源码状态、环境、实际命令、结果和未覆盖范围。
当前验证摘要可更新，但不把以前执行的结果写成本次重测；过时结果不成为当前保证。
完整日志、截图、临时验证脚本和产物留在忽略目录，如 `build/verification/`，注明其本机可用性。
非阻塞警告说明来源与影响；失败明确到阶段，不把部分成功写成整条链路通过。

## 开发历史

`doc/history/` 在用户明确要求或同意保存思考、方案、历史、快照、实验、验收或交接时新增内容；授权迁移现有非事实文档同样有效。
普通实现、测试、重构、文档同步或整理目录都不自动授权新增记录。
AI 可说明拟记录内容与保留价值后询问，不必每次询问；未获同意留在会话，已有授权不重复确认。
用户明确指定其他保存位置时遵循其要求。

新增文件及附件使用 `YYYY-MM-DD-主题.扩展名`，主题为小写英文、数字和连字符。
日期优先用用户指定日期或材料原日期；新记录未指定时用当天，附件沿用所属记录日期。
首次归档无明确日期的已有材料时用 Git 首次保存日期并说明来源。
记录注明日期、状态、范围和来源，关联所属当前页面与原始证据；不默认保存提交 hash。
来源含未提交工作树或会话内容时明确写出，不能宣称已提交源码包含尚未提交的讨论。
区分用户明确目标、助手建议、文档原有方案和源码证据；保存方向变化及取舍，不把全部内容归成用户已确认决定。
经授权迁移时，先保存职责、依赖、数据流、接口、所有权、生命周期和必要理由，再清理当前页面。归档可保留方案所需事实背景，但不是第二份当前权威说明。

已有历史及附件保持原样，不修改、补注、改名或删除；新的实现事实更新当前所属页面，新的思考按授权另存历史。
历史内旧源码路径按记录日期、来源和版本查阅 Git 历史，后续路径变化不回写历史。
有历史时在 overview 维护索引；目录整理本身不另写历史。

## 更新与检查

更改行为、接口、生命周期或流程时同步所属文档；移动或合并前检查引用和独有内容。迁出方案先核对历史内容已保存，再删除当前正文。
改归属时同步 overview、AGENTS、README、技能和代码入口，不为旧文件保留第二份正文。

在仓库根执行：

```powershell
python tools/check_docs.py
git diff --check
```

检查器只扫描 Git 跟踪及未忽略的新文件，校验目录归属、页面头部、代码锚点、本地链接、文档路径和代码入口数量。
历史检查名称与头部，其内部链接和锚点按记录基线理解；当前文档指向历史的链接仍必须有效。
不校验网页、Markdown 章节片段或技术语义，后者须人工对照源码。检查当前文档中的建议/未来式表述和不存在的接口、模块、流程，逐项核对而非机械替换；检查移走章节的链接和历史原文完整性。修改检查器时验证它能发现缺失引用。
检查本次文档改动没有加入用户未明确要求保存的 Git hash，检查范围包含链接 URL。
纯文档与注释路径整理不需要重编译 C++ 或启动游戏；涉及行为改动则运行对应检查并如实报告。
